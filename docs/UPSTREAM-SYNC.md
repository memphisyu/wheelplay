## 日常更新：先评估，再按依赖合入

1. 检查未提交修改并获取两边真实最新提交，不重置、覆盖或切换用户当前工作分支。对照台账阅读差异、测试及依赖，区分缺失功能与已适配功能。
2. 独立修复优先原提交摘取，保留来源（适合时使用 `cherry-pick -x`）；耦合设置、资源或网页的功能先列适配范围，经确认后再做。不要重复摘取已适配功能。
3. 完成后更新台账、验证结果和待实车项目。测试/CI 改动不自动提升版本号；发布须另行明确授权，发布时同步 GitHub/Gitee。

## 差异扩大时：在独立集成分支做一次完整对齐

当多个待引入功能依赖同一套新架构，或每轮重复解决同样冲突时，先评估一次完整迁移。冲突文件数量是工作量信号，不能单凭数量决定是否合并。

在用户确认范围后，从当前 `xpeng` 建独立集成分支/工作区，固定双方提交并用 `merge-tree` 预检查。真正合并时逐项处理已适配功能，避免 mDNS 等出现两套实现。Compose/双语迁移必须有专门适配方案；仍暂缓这些功能时继续选择性同步。集成分支通过代码审查、自动检查和实车验证后，再以保留历史的合并方式进入 `xpeng`，记录新的完整上游基线。失败时保留集成分支取证，已发布主线继续使用原版本。

逐步把定制集中到清晰边界：浏览器媒体/封面与音频、画面尺寸策略、Root/后台连接、证书导入和升级渠道。修相关功能时再抽取接口，避免为追上游一次性重写稳定模块。可以上游化的通用修复单独整理；向上游提交需另行授权。

## 合并门槛

- 自动：shared/common 单元测试、网页 Node 测试、Android lint、APK 构建、测试 APK 编译和 API 28/36 HTTP 冒烟测试。HTTP 测试验证入口、媒体资源及响应头，不等于浏览器执行或实车验证。
- 实车：G9/15T 持续音乐、静音恢复、封面与方向盘、分屏/全屏切换、锁屏后台与自动重连；涉及 VPN/mDNS 时补对应车机网络验证。
- 发布：包名与签名兼容、覆盖安装、HTTPS/认证导入、升级下载渠道；不公开私钥或认证身份。大规模迁移先发候选版，验证后再转正式版。
